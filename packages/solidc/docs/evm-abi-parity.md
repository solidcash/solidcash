# EVM ABI byte-parity (evmCompat mode)

Status: SPEC (design). Grounded against `/Code/solidity` @ 0.8.36 (`libsolidity/codegen/ABIFunctions.cpp`,
`libsolidity/ast/Types.cpp`, `docs/abi-spec.rst`, `libsolutil/FunctionSelector.h`) and the current SolidCash
codegen. Nothing here is implemented yet.

## 0. Goal and scope

Make the whole `abi.*` family produce **byte-identical** output to the EVM, under an opt-in `evmCompat` mode,
by converting at the encoding boundary. The native number system (little-endian sign-magnitude BigInt) is NOT
touched - only the bytes emitted at the abi boundary change.

In scope (all must reach byte-parity):
- `abi.encode`, `abi.encodePacked`
- `abi.encodeWithSelector`, `abi.encodeWithSignature`, `abi.encodeCall`
- `abi.decode`, `abi.decodeAt`
- the same standard encoder as it backs **external-call args, return data, and event (non-indexed) data**

Non-goals / deliberate divergences (section 8):
- native `address` (a full variable-length locking bytecode) has no 20-byte EVM analogue
- `pubkey` (BCH-only, 33 bytes) has no EVM ABI type
- `fixed`/`ufixed` - not encodable in solc either (`leftAlignFunction` / `cleanupFunction`
  `solUnimplemented`), so out for both.

### Why a separate mode

The current `abi.*` emits a BCH-native wire format - minimal-pushdata concatenation, little-endian
sign-magnitude numbers, sha256 selectors, variable-length addresses, no head/tail, no 32-byte slots
(`visitAbiEncode` GTT:7491, `emitPushdataEncode` GTT:7718, `computeFunctionSelector` utils/state.ts:1410). It
is internally consistent and self-describing but diverges from EVM on nearly every axis. `evmCompat` is a
**parallel encoder path** selected by the flag, not a patch to the native one; the native format stays the
default (it is denser and needs no keccak). No existing test pins abi output bytes or compares to a real EVM
vector, so adding the parallel path breaks nothing.

## 1. Design principles

1. **Boundary conversion, never internal.** The BCH VM's arithmetic opcodes are hardwired to LE sign-magnitude
   `CScriptNum`; storing values as BE two's-complement would force a conversion on every `OP_ADD`. So the
   internal representation stays native and we convert only where a number crosses into an abi byte string.
2. **Gated, temporarily.** A compiler option `evmCompat` scaffolds this work; it is **dropped once the parity
   suite is green**, at which point EVM-faithful abi encoding becomes the default. The gate is an implementation
   convenience, not a permanent switch. IMPORTANT: nothing else may be gated behind `evmCompat` without explicit
   user sign-off - it is scoped to this encoding work only.
3. **Reuse existing primitives.** `emitToTwosComplementBytes` / `emitFromTwosComplementBytes` (GTT:4728, 4745)
   and `OP_REVERSEBYTES` (GTT:4782) already exist for bitwise ops; the abi path wires them in via the word
   primitives below rather than inventing new ones.
4. **Prove with vectors.** Parity is asserted against reference bytes generated by ethers/solc (section 10),
   not just round-trip.

## 2. The word primitives (the foundation)

Every 32-byte slot in the standard encoder is one of two primitives. Getting the pad direction right is
load-bearing: **numbers LEFT-pad (value in the low/right bytes), `bytesN`/`function` RIGHT-pad (value in the
high/left bytes)** (`abi-spec.rst:213-222`).

### 2.1 encodeWord256 (numbers: left-pad, big-endian, two's-complement)

The 33-vs-32 quirk: a positive `uint256 >= 2^255` needs a 33rd byte on BCH (the sign byte of LE sign-magnitude),
because the top bit of byte 32 would otherwise read as negative. EVM has no sign byte. The uniform encoder
(works for every `uintN` incl. the high-bit `uint256`, no branching):

```
encodeWord256(uint x):   x  OP_33 OP_NUM2BIN  OP_32 OP_SPLIT OP_DROP  OP_REVERSEBYTES
   NUM2BIN to 33 always succeeds (x < 2^256 fits positive in 33 bytes; byte[32] = 0x00 sign pad)
   SPLIT at 32, DROP the 0x00 sign byte      -> low 32 magnitude bytes, LE
   REVERSEBYTES                              -> 32-byte big-endian, EVM-identical
```

`OP_NUM2BIN(x, 32)` directly would FAIL for `x >= 2^255` (cannot fit signed) - that is the trap to avoid.

Signed `intN`: first map to the 256-bit two's-complement pattern (`x < 0 ? x + 2^256 : x`, i.e.
`emitToTwosComplementBytes` extended to 256-bit width), then the same 33-split-reverse. For narrower `intN`/
`uintN` the value never reaches the 32-byte top bit, so `OP_NUM2BIN(x, 32) OP_REVERSEBYTES` suffices; the
33-split path is a correct superset, so implement once and use uniformly (optionally optimize widths < 256).

```
decodeWord256(bytes32 w) -> uint:   w  OP_REVERSEBYTES  <0x00> OP_CAT  OP_BIN2NUM
   reverse to LE, append 0x00 sign byte -> stays positive even when top bit set
decodeWord256 signed:               w  OP_REVERSEBYTES  OP_BIN2NUM ; then 2C->sign-magnitude
   (if top bit set: value = magnitude - 2^256) via emitFromTwosComplementBytes
```

Internally the BCH value stays 33 bytes for `>= 2^255` (unavoidable, correct); only the encoding is 32.

### 2.2 encodeFixedBytes (bytesN / function: right-pad, no reverse)

`bytesN` is a raw byte string, EVM-left-aligned (data in the high/first bytes). BCH stores it in the same
order, so:

```
encodeFixedBytes(bytesN b):   b  <zeros(32 - N)> OP_CAT        # right-pad, NO reverse
```

External `function` type = 24 bytes (20-byte address ++ 4-byte selector) right-padded to 32
(`Types.cpp:3291-3294`); on BCH this type has no native analogue (address is not 20 bytes) - treat as an
EVM-source-only shape or reject (section 8).

### 2.3 Value-type word table

| Type | EVM word (32 bytes) | Primitive |
|---|---|---|
| `uintN` | left-pad BE | `encodeWord256` |
| `intN` | left-pad BE two's-complement, sign-extended | `encodeWord256` (signed) |
| `bool` | `uint8` 0/1, left-pad | `encodeWord256` of 0/1 (native true is `OP_1`=0x51; normalize to 1) |
| `enum` | `uint8`, left-pad, value `< memberCount` | `encodeWord256` of the ordinal |
| `bytesN` (1..32) | right-pad | `encodeFixedBytes` |
| EVM `address` (`uint160`/`bytes20`-shaped) | 20 bytes left-pad (as `uint160`) | `encodeWord256` of the uint160 value (NOT `encodeFixedBytes` - address left-pads, `bytes20` right-pads; do not conflate) |
| native `address` | n/a (variable locking bytecode) | dynamic, section 8 |
| UDVT | underlying | primitive of the underlying |
| `contract` | as `address` | `encodeWord256` of uint160 |

Number-type semantics (ALREADY IMPLEMENTED): `int`/`uint` are fixed-width `int256`/`uint256` with EVM overflow -
checked reverts (emitIntBoundsCheck GTT:5292), `unchecked` wraps mod 2^N (emitIntWrap GTT:5330, the standard
offset-wrap = two's-complement); `bigint` is the BCH-native UNBOUNDED integer (parseType types.ts:584-586). So
the abi encoder always sees a fixed-width value and the word primitive is its abi side. `bigint` has no EVM ABI
type -> reject in the parity encoder. Remaining number-parity work is VERIFICATION of EVM edge cases (div/mod
sign+rounding, shifts, `**`, INT_MIN) via reference vectors, not a build.

## 3. The head/tail algorithm

The standard encoder is a recursive, self-contained-blob encoder. Every aggregate produces a byte blob whose
internal dynamic offsets are relative to that blob's own start, so blobs compose without patching
(`ABIFunctions.cpp:70-106`; the load-bearing rule is `offset = sub(tail, headStart)`, headStart = the start of
THIS aggregate, not the message - `abi-spec.rst:185`, nested example `:353-463`).

### 3.1 Dynamic vs static classification (`isDynamicallyEncoded`, `Types.cpp:1802,2288`)

Dynamic: `bytes`, `string`, `T[]`, `T[k]` where T is dynamic, struct/tuple containing any dynamic member.
Everything else is static.

### 3.2 Head slot size (`calldataHeadSize`, `Types.h:256`)

- dynamic Ti -> 32 (an offset)
- static Ti -> its **full** static encoded size `calldataEncodedSize(true)` (a static struct of 3 words takes
  **96** bytes in the head, inline - not 32). So `headSize` is a compile-time constant for any statically
  shaped argument list.

### 3.3 Encoder (pseudocode)

```
encode(value, T) -> blob:                       # self-contained, offsets relative to blob start
  value type            -> word primitive (section 2)           # 32 bytes
  bytes/string          -> encodeWord256(len) ++ rightPad32(data)
  T'[k] fixed           -> encodeTuple([e_i], [T']*k)           # no length word
  T'[] dynamic          -> encodeWord256(n) ++ encodeTuple([e_i], [T']*n)
  struct/tuple          -> encodeTuple(members, memberTypes)

encodeTuple(vals[], types[]) -> blob:
  headSize = SUM headSlotSize(types[i])         # compile-time for static shapes
  head = ""; tail = ""; offset = headSize
  for i:
    b = encode(vals[i], types[i])
    if dynamic(types[i]):
      head ++= encodeWord256(offset)            # offset word
      tail ++= b
      offset += OP_SIZE(b)                       # runtime, via OP_SIZE
    else:
      head ++= b                                 # static: inline full encoding
  return head ++ tail
```

`rightPad32(data)` pads to a multiple of 32 (`roundUp = and(add(len,31), not(31))`, `ABIFunctions.cpp:666`).

### 3.4 On-stack vs `__yulmem`

The pseudocode is expressible entirely with `OP_CAT` (concatenate), `OP_SIZE` (tail lengths), and arithmetic
(offset accumulation) - no random-access memory needed, because each blob is self-contained. For fully static
shapes `headSize` and structure are compile-time; only the values are runtime. This on-stack streaming encoder
is the recommended default.

Alternative: build into the existing `__yulmem` linear buffer (base 0x80, `mstore`/`mload`) and mirror solc's
memory encoder verbatim. Heavier, but a clean fallback for pathological deep nesting where stack juggling of
many intermediate blobs gets awkward. Decide per-implementation-phase; start on-stack.

## 4. Standard per-type encoding (target vs current)

| Type | EVM standard (target) | Current SolidCash | Delta |
|---|---|---|---|
| `uintN`/`intN` | 32B, left-pad BE, int two's-complement | minimal pushdata, LE sign-mag, var-len (uint256=33B) | word primitive |
| `bool` | 32B, 0/1 | 1B, true=0x51 | word primitive, normalize |
| `bytesN` | 32B right-pad | `<N><data>` (1+N) | encodeFixedBytes |
| `bytes`/`string` | 32B len + data right-pad to 32-mult (in tail; offset in head) | `<len><data>` pushdata, no pad, no offset | head/tail + rightPad32 |
| `T[k]` fixed | element tuple, no length | `pushdata(count) ++ packed elems` (visitArray GTT:5129) | head/tail, per-elem 32B |
| `T[]` dynamic | 32B len + element tuple (in tail; offset in head) | same blob as fixed | head/tail + length word + offset |
| struct/tuple | member tuple (head/tail) | inline concat of field blobs | head/tail |
| EVM `address` | 20B left-pad to 32 | variable locking bytecode | section 8 |
| `enum` | `uint8` 32B | int-like | word primitive |

## 5. Packed encoding (`abi.encodePacked`)

Rules (`tupleEncoderPacked` `ABIFunctions.cpp:118-191`; `abi-spec.rst:750-801`):

- No head/tail, no offsets, no length prefixes; single advancing cursor.
- Each value at its **natural** width, big-endian: `uintN`/`intN` = N/8 bytes (int two's-complement), `address`
  = 20, `bytesN` = N, `bool` = 1, `enum` = 1.
- Dynamic `bytes`/`string`/`T[]` are in-place with **no length word** and (for bytes/string) **no trailing
  pad** (`lengthPadded = padded ? roundUp : length`, `:666`).
- THE EXCEPTION: array elements and struct members are **padded to 32** even in packed mode
  (`subOptions.padded = true`, `:549`, `:928-929`). So `abi.encodePacked(uint16[])` pads each element to 32 but
  emits no length prefix.
- solc REJECTS in packed mode: any struct, and arrays whose base is a dynamically-sized array
  (`TypeChecker.cpp:55-68`). Mirror these rejections under `evmCompat` (compile error), plus the >=2-dynamic
  ambiguity warning.

Current SolidCash packed (`visitAbiEncodePacked` GTT:7512) already matches EVM for `bytesN` (raw N bytes),
`bool` (1B 0/1), and dynamic bytes/string (raw, no length). The deltas: numbers need BE + two's-complement +
natural width (currently LE sign-mag width `ceil((bits+1)/8)`), address needs the section-8 decision, and the
array element-pad-to-32 exception must be added.

## 6. Selectors and canonical signatures

### 6.1 Selector = `keccak256(canonicalSignature)[:4]`

The high-order (big-endian) first 4 bytes (`FunctionSelector.h:30-33`). Current SolidCash uses **sha256**
(`computeFunctionSelector` utils/state.ts:1410) - this is the parity break for `encodeCall`,
`encodeWithSignature`, `.selector`, `msg.sig`.

- Constant signatures (the overwhelming majority: `encodeCall`, literal `encodeWithSignature`, `.selector`,
  `msg.sig`) -> fold the **real keccak at compile time** (a keccak lib is reachable from the compiler;
  `@noble/hashes/sha3` verified available, or vendor `keccak-poc/keccak.mjs`). This is the same real-keccak
  constant-folding as the storage-parity work; zero on-chain cost.
- Runtime signature string (`encodeWithSignature(nonLiteral, ...)`) -> needs real keccak of runtime bytes =
  the keccak side-car (bounded, 1 call/input; already shipped for `keccak256`). Rare.

### 6.2 Canonical-signature normalization (must match solc exactly)

`FunctionType::externalSignature` `Types.cpp:3646-3682`: `name '(' join(canonicalTypeNames, ',') ')'`, no
spaces, return types excluded. Normalization (`signatureInExternalFunction` / `interfaceType`):

- `uint` -> `uint256`, `int` -> `int256` (aliases resolve to 256-bit).
- strip data location (`memory`/`calldata`/`storage`).
- `enum` -> `uint8`; UDVT -> underlying; `contract` and `address payable` -> `address`.
- arrays -> `T[]` / `T[k]`; `bytes`/`string` literal.
- struct -> tuple `(T1,T2,...)`, recursive.
- external `function` -> `function`.

SolidCash's `computeFunctionSignature` (utils/state.ts:1401) builds the string from `type.toString()`; under
`evmCompat` it must emit these exact canonical names (audit `toString` for `uint`->`uint256` etc.).

### 6.3 Builders

- `encodeWithSelector(bytes4 sel, ...)` = `sel ++ encodeStandard((...))`.
- `encodeWithSignature(string sig, ...)` = `encodeWithSelector(bytes4(keccak256(bytes(sig))), ...)` - solc does
  NOT normalize the caller's string (garbage in, garbage out); match that.
- `encodeCall(fnPtr, (args))` = `encodeWithSelector(fnPtr.selector, (args))` with a full compile-time
  type-check of args vs the function's parameters.

## 7. abi.decode (inverse + validation)

Mirror `tupleDecoder` (`ABIFunctions.cpp:192-260`):

- Head-fits check: revert if `dataEnd - headStart < headSize`.
- Dynamic element: read the 32-byte offset (bound `offset <= 2^64-1`), decode at `headStart + offset`.
- Value-type validation ("clean bytes"): the loaded word must equal its cleaned form or revert - `bool` in
  {0,1}, `address`/`uintN` high bits zero, `intN` correctly sign-extended, `bytesN` low bits zero, `enum`
  `< memberCount`.
- `bytes`/`string`/array length bounds: `offset + roundUp(len)*stride <= end`.

Word decode uses `decodeWord256` (section 2.1). SolidCash `abi.decode` today (GTT:7652) trusts self-describing
pushdata framing with no offset table and no bounds checks - the `evmCompat` decoder is a separate path that
reads EVM head/tail with these validations.

## 8. Type gaps (deliberate, documented divergences)

### 8.1 address = full locking bytecode (variable length)

A SolidCash `address` is the entire scriptPubKey (P2PKH `76a914<20>88ac` = 25B, P2SH32 `aa20<32>87` = 35B,
P2SH20 = 23B, or an arbitrary covenant script) - not a hash, not a fixed width (`AddressType`, utils/types.ts:10,
no fixed width). So:

- **native `address`** -> encode as a **dynamic** value (length word + locking bytecode right-padded to a
  32-multiple; offset in the head). Uses "as much space as needed"; NOT byte-identical to an EVM 20-byte
  address, because a BCH address genuinely is not 20 bytes. This makes `address` a dynamic type in the head/tail
  layout under `evmCompat`.
- **EVM-shaped address value** (`uint160` / explicit `bytes20`, the cross-chain / EVM-source path) -> 20 bytes
  left-padded to one 32-byte word (`encodeWord256` of the uint160), byte-exact with Ethereum.

The compiler chooses by static type: a value typed `address` -> dynamic locking bytecode; a value typed
`uint160`/`bytes20` -> the EVM word form. The EVM-shaped path is reached via the existing `uint160` /
`bytes20(address)` casts, which ALREADY emit a warning/error (the ecrecover / address-cast work) - reuse that,
do not add new native-address abi machinery.

NOTE: `platform-differences.md:127` currently mis-states this ("Addresses are p2sh32 (a 32-byte script hash)");
fix to "the full variable-length locking bytecode."

### 8.2 pubkey (33B), fixed-point

`pubkey` has no EVM ABI type -> reject in `evmCompat` (or, opt-in, encode as dynamic bytes). `fixed`/`ufixed`
are unencodable in solc too -> reject.

### 8.3 Hash-value comparisons and bytesN <-> uintN cast endianness (Solidity-style)

`keccak256(x) == 0xLITERAL` (also `sha256`, Merkle-proof checks, commitments) is the most common hash comparison
and must be Solidity-style. Two distinct cases, only one of which needs a fix:

- **Direct byte-string comparison `bytesN == bytesN-literal` - ALREADY CORRECT (both modes).** `keccak256(x)`
  returns the digest in Ethereum byte order (real-keccak side-car, validated vs EVM; `keccak-library.ts`). A hex
  literal `0xABCD...` is a `HexLiteralNode` carrying its SOURCE-order bytes and is emitted verbatim
  (`GTT:6705`). So both sides are 32-byte strings in the same (Ethereum/source) order and `==` is a byte
  `OP_EQUAL` - Solidity-correct with no byte-order flip. This is NOT a quirk; lock it with a conformance test so
  it cannot regress.
- **Numeric-cast comparison `uintN(hash)` - the actual quirk, fixed under evmCompat.** `uint256(keccak256(x))`
  reads the digest LITTLE-endian on BCH (`bytes32(uint)` low byte at index 0) but Solidity reads it BIG-endian.
  So hash-as-number code diverges: sorted-pair Merkle (`a < b ? keccak(a,b) : keccak(b,a)`), `uint256(hash) % n`,
  threshold/difficulty checks. Under `evmCompat`, `bytesN <-> uintN` casts use EVM (big-endian) order - the same
  `encodeWord256`/`decodeWord256` boundary - so `uint256(keccak256(x))` matches Solidity. The cast is the single
  place the flip is needed; the direct byte comparison above is not.

Both go in the conformance corpus (section 10).

## 9. Implementation architecture

- **Flag:** `CompilerOptions.evmCompat` (compiler.ts). Thread into GTT and the abi visitors.
- **Encoder path:** new `emitAbiStandardEncode(type)` / `emitAbiPackedEncode(type)` selected by the flag in
  `visitAbiEncode` (GTT:7491), `visitAbiEncodePacked` (7512), `visitAbiEncodeWithSelector/Signature/Call`
  (7569/7576/7600); native path unchanged when the flag is off.
- **Word primitives:** `emitEncodeWord256` / `emitDecodeWord256` / `emitEncodeFixedBytes`, built on
  `emitToTwosComplementBytes` (GTT:4728) + `OP_REVERSEBYTES`.
- **Head/tail:** `emitAbiTuple(types[])` implementing section 3.3 with `OP_CAT`/`OP_SIZE`.
- **Selector:** real-keccak fold in `computeFunctionSelector` (utils/state.ts:1410) under `evmCompat`; canonical
  names in `computeFunctionSignature` (state.ts:1401). Runtime-signature keccak via the side-car.
- **SDK mirror:** `packages/utils/src/state.ts` (`encodePushdataValue`, `packFixedWidthArray`) and `data.ts` need
  an `evmCompat` encoder/decoder so off-chain building and `abi.decode` results match on-chain. This is the SDK
  half of the boundary.
- **decode:** `emitAbiStandardDecode` with the section-7 validations.

## 10. Testing: differential conformance (solc + solidc, Tevm + libauth)

Parity is established by DIFFERENTIAL execution, not just static vectors: a corpus of tests where the SAME
source compiles under BOTH solc (to EVM) and solidc (to BCH), both VMs evaluate the same function, and the
results must be VALUE-IDENTICAL. This proves the whole parity surface (abi encoding AND number semantics) end to
end, not just the encoder.

### Harness
- ONE corpus of small contracts in the common Solidity/SolidCash subset, each exposing pure functions that
  return the value(s) under test (an arithmetic result, an `abi.encode(...)` blob, a 4-byte selector).
- EVM side: compile with solc, then deploy + call in **Tevm** (tevm.sh) - a TypeScript, **node-less, in-memory
  EVM** (no RPC node, evaluates in-process) - and read the decoded return / raw returndata.
- BCH side: compile with solidc under `evmCompat`, run the function in the libauth VM (the existing test
  substrate), extract the result from the trace.
- Assert: **value-identical** decoded returns for arithmetic/semantic cases; **byte-identical** raw output for
  `abi.encode`/`encodePacked`/selector cases (the byte-parity goal). A mismatch localizes the divergence to one
  function.

### Corpus coverage
- ABI per-type matrix (sections 2/4): each value type at boundary values (0, 1, max, `2^255`, `2^255-1`,
  negatives), `bytesN` for all N, dynamic `bytes`/`string` at lengths {0,1,31,32,33}, `T[k]`/`T[]`, nested
  structs, mixed static+dynamic tuples.
- Selectors: `encodeWithSignature` / `encodeCall` / `.selector` incl. `uint`/`int` alias normalization; assert
  the 4-byte selector equals solc's.
- Number-parity checklist (section 12): signed `>>`, `/`/`%` sign+rounding, `**`, INT_MIN negation,
  `type(T).min`/`.max`, `unchecked` wrap at 2^256 - compare returned VALUES.
- Hash comparisons (section 8.3): `keccak256(abi.encodePacked(x)) == <literal>` (byte-string, must already pass)
  AND `uint256(keccak256(x))` ordering/modulo + a sorted-pair Merkle root (numeric cast, needs BE under
  evmCompat) - assert value-identical on solc + solidc.
- Round-trip: `abi.decode(evmEncode(x)) == x`, and cross-decode a Tevm-produced blob in solidc (and vice versa).

### Notes
- The corpus source is the single source of truth: a construct that will not compile on both is outside the
  common subset (document it - e.g. `bigint`, native `address`).
- Add `tevm` as a dev-dependency of the test package; it runs in-process, so the suite stays fast, hermetic, and
  node/network-free.
- Keep the existing native-mode abi tests (they assert no bytes); this differential suite runs under `evmCompat`.

## 11. Phasing

1. **Word primitives + static tuples.** `encodeWord256`/`encodeFixedBytes`/`decodeWord256`; `abi.encode`/
   `decode` for value types and all-static tuples (left/right pad, BE, two's-complement, the 33->32 handling).
   Vector-test against ethers.
2. **Dynamic head/tail.** `bytes`/`string`/`T[]` + mixed static/dynamic tuples + nested (the offset engine).
3. **Selectors.** Real-keccak fold for constant signatures + canonical normalization; `encodeCall`/
   `encodeWithSignature`/`.selector`/`msg.sig`; runtime-signature side-car.
4. **Packed.** Natural-width BE + the element-pad-to-32 exception + the solc rejections.
5. **address + gaps.** The dynamic native-address encoding + `uint160`/`bytes20` EVM form; reject pubkey/fixed.
6. **SDK mirror + external-call/return/event encoding** under the flag.

Phase 1 alone gives byte-parity for the flat value-type case that covers most `keccak256(abi.encode(...))` and
event-data uses.

## 12. Decisions (resolved 2026-07-15, user)

- **Flag = temporary scaffold.** `evmCompat` is a distinct option used ONLY to bring this work up; it is
  DROPPED once the parity suite is green, at which point EVM encoding is the default. No other feature may be
  gated behind it without explicit user permission.
- **native address in abi:** encode as dynamic locking bytecode; the EVM-20-byte form is reached by an explicit
  `uint160`/`bytes20(address)` cast, which ALREADY emits a warning/error (ecrecover / address-cast work) - reuse
  it, do not add new native-address abi machinery.
- **Number semantics (ALREADY IMPLEMENTED, verify parity):** `int`/`uint` = fixed-width `int256`/`uint256`,
  checked reverts (emitIntBoundsCheck GTT:5292) / `unchecked` wraps mod 2^N (emitIntWrap GTT:5330 = offset-wrap =
  two's-complement); `bigint` = unbounded native int (parseType types.ts:584-586). Structurally EVM-parity. ABI:
  int256/uint256 -> `encodeWord256` (the 33->32 primitive bridges the on-stack LE value); `bigint` rejected.
  Remaining = VERIFY EVM edge cases via reference vectors (an audit, not a build): signed `>>`
  arithmetic-vs-truncated (highest risk), `/` `%` sign+rounding, `**`, INT_MIN negation, and `type(T).min`/`.max`
  boundaries (`uint256.max`=2^256-1 the 33-byte value, `int256.min`=-2^255). `type(T).min/max` already emit
  `IntType.minValue/maxValue` (GTT:7155, EVM-correct values); the audit confirms they compare/encode correctly.
- **Encoder substrate:** UNDECIDED - pick by least bytecode + least compute budget. Lean on-stack streaming
  (CAT/SIZE) for the common flat/static case; measure `__yulmem` only where deep nesting proves cheaper. Confirm
  empirically in Phase 1.
- **`bytesN` internal byte order:** confirm SolidCash stores `bytesN` left-aligned (data-first) so
  `encodeFixedBytes` is a pure right-pad with no reverse (verify against a `bytes4` selector vector in phase 1).
