# Source maps and dynamic function dispatch

This note documents how SolidCash generates source maps, how the move to dynamic function dispatch
(`OP_DEFINE`/`OP_INVOKE`) fragmented them, and how the reference Solidity compiler avoids that. It is the
output of an investigation; the "Recommendations" section lists concrete fixes, none of which are implemented yet.

## TL;DR

- A function's per-instruction location data is **not deleted** - for multi-function contracts it is moved out of
  the top-level map into a per-function map (`artifact.debug.functionDebug[selector].sourceMap`), and SolidCash's
  own debuggers stitch it back.
- But the top-level `artifact.debug.sourceMap` **collapses each extracted function body to a single push**, and
  the map format has **no jump-type field**, so the two tiers are not stitchable in-band. Any consumer that reads
  only `debug.sourceMap` (external tooling, explorers) sees no per-function detail. That is the "lost somewhat".
- Solidity never splits: one assembly, every instruction inline with its own location plus a jump-type
  (`i`/`o`) tag. Nothing collapses; debuggers rebuild the call stack from the tags.

## SolidCash source-map format

Generated by `generateSourceMap` (`packages/utils/src/source-map.ts:28`). One `;`-separated entry per opcode:

```
sl:sc:el:ec:h
```

- `sl:sc` start line/column, `el:ec` end line/column (line/column, not Solidity's byte-offset:length).
- `h` position hint: `0` = START, `1` = END - where to place the instructions that surround a child AST block
  (function declarations, if/else), so the surrounding ops attach to the block's opening vs closing.
- Compression is the same trailing-equal-field omission as Solidity: an empty field repeats the previous value;
  a missing `:` means all following fields are empty.
- There is **no source-file index** (single compilation unit) and **no jump-type field**.

The map is parsed back by `sourceMapToLocationData` and consumed for the bitauth/CashAssembly debug view by
`buildLineToOpcodesMap` (`packages/utils/src/bitauth-script.ts:8`).

## How Solidity does it (reference: `../solidity`)

Solidity keeps **one assembly with every instruction inline** and calls functions via `JUMP` within that same
stream - it never extracts a function body into a separate code object. Each instruction
(`libevmasm/AssemblyItem.h`) carries its own metadata:

- `SourceLocation m_location` - per-instruction source range (`AssemblyItem.h:200,210`).
- `enum JumpType { Ordinary, IntoFunction, OutOfFunction }` (`AssemblyItem.h:69,248`).
- `m_modifierDepth` (`AssemblyItem.h:234`).

`AssemblyItem::computeSourceMapping` (`libevmasm/AssemblyItem.cpp:432`) emits one entry per instruction:

```
s:l:f:j:m      // start, length, source-file index, jump (-, i, o), modifier depth
```

and runs over **all** items for both the creation and runtime assemblies
(`libevmasm/EVMAssemblyStack.cpp:60,65`).

The key property: because a function is *called by JUMP inside the same instruction stream*, the function body's
instructions keep **their own** locations, the call-site JUMP is tagged `IntoFunction` (`i`) with the call-site
location, and the return JUMP is tagged `OutOfFunction` (`o`). **No location is ever collapsed.** A debugger
reconstructs the call stack purely from the `i`/`o` tags in the one map.

## SolidCash's architecture (two tiers, due to OP_DEFINE extraction)

Multi-function contracts use `OP_DEFINE`/`OP_INVOKE` dynamic dispatch: each entry-point function body is compiled
into its **own** bytecode blob, registered under its 4-byte selector and invoked at spend time. This splits the
source map into two tiers:

1. **Top-level / dispatcher map** - `artifact.debug.sourceMap`
   (built in `compiler.ts:206` from the optimised main bytecode).
2. **Per-function maps** - `artifact.debug.functionDebug[selectorHex].sourceMap`
   (one per entry point), plus the raw bodies in `artifact.functionBodies[selectorHex]`
   (`compiler.ts:212-217`).

Per-function capture happens in the sub-traversal (`generation/GenerateTargetTraversal.ts`):

- the body is compiled with full per-instruction location data, normalised, optimised, and its map stored:
  `entryPointDebugInfo.set(selectorHex, { sourceMap: generateSourceMap(optimisationResult.locationData), ... })`
  (lines `1151, 1169-1177`).

### Where it collapses

After capturing the body's own map, the body is injected into the **main** bytecode as a single data push:

```ts
// generation/GenerateTargetTraversal.ts:1178
this.emit(bodyBytecode, locationData);   // one location entry for the ENTIRE function body
this.emit(func.functionSelector!, locationData);
this.emit(Op.OP_DEFINE, locationData);
```

So in `artifact.debug.sourceMap` the whole function body is one opaque push mapping to one source location (the
`OP_DEFINE` site). For a multi-function contract the top-level map is therefore mostly the dispatcher; the bodies
are flattened. This is *correct* for the main instruction stream (the blob really is one push there), but it
means the top-level map alone no longer describes function execution.

### What is preserved vs lost

Preserved - the per-function maps are complete and **are** stitched by both SolidCash debuggers:

- SDK debugger: `packages/solidcash/src/debugging.ts:462` (`functionDebug[selector].sourceMap`), plus per-selector
  `requires`/`logs` at `:438,:447,:115`.
- bitauth/libauth IDE template: `packages/solidcash/src/libauth-template/utils.ts:117-124`
  (`formatFunctionBodyForDebugging`).

Lost / degraded:

1. **Top-level map is collapsed** for every extracted body - any consumer reading only `debug.sourceMap` loses
   per-function detail.
2. **No unified, self-describing map.** The format has no jump-type field, so nothing in the map says "execution
   transferred into a function-body stream." Consumers must know to switch to `functionDebug`, and they identify
   the selector out-of-band (e.g. from the unlocking-script id, `debugging.ts:96`).
3. **Alignment fragility.** The body map is `subTraversal.locationData.slice(0, normalizedOutput.length)` after an
   asm round-trip (`GenerateTargetTraversal.ts:1151`); it assumes 1:1 opcode<->location and is not asserted,
   unlike the main path's dual-optimizer equality check.

This is inherent to the `OP_DEFINE`/`OP_INVOKE` model: bodies are *separate executable streams*, so a single
Solidity-style inline map is not directly achievable without giving up extraction. The fix direction is to make
the two-tier structure self-describing and losslessly stitchable, not to un-split.

## Recommendations (not yet implemented)

1. **Add a jump/stream-type field to the map format** - extend entries to `sl:sc:el:ec:h:j` with
   `j` in `-` / `i` (into a body via `OP_INVOKE`) / `o` (return) / optionally `d` (the `OP_DEFINE` body push).
   Direct Solidity parity; makes the tiers stitchable in-band instead of selector-guessed. Touches
   `source-map.ts` (encode/decode) and the `emit` sites in `GenerateTargetTraversal.ts`.
2. **Offer a merged map view** - a helper that concatenates the dispatcher map with each body's map at the body's
   blob offset, so external tools can get one per-instruction map for the whole contract. Keep `functionDebug`
   for execution.
3. **Harden the body slice** (`GenerateTargetTraversal.ts:1151`) - thread `locationData` 1:1 through the asm
   round-trip + optimiser and assert `locationData.length === script.length`, mirroring the main path's invariant.
4. **Document the two-tier contract** in the artifact schema - `debug.sourceMap` = dispatcher stream;
   `functionDebug[selector].sourceMap` = the executed body stream - so third-party consumers stitch correctly.

Suggested first step: (1) + (3) - the jump-type tag plus the alignment assertion - which together make the
fragmentation explicit and safe, after which the merged view (2) is mechanical.
